# Config: TypeScript, the `catwm` module and overrides

`ConfigStore` (`Config/Script/`) owns the config that CatWM runs. It reads `catwm.config.ts` from `Instance.configFolder`, then `catwm.overrides.json`, and gives `WindowManager` one `Config`.

## Parts (`Sources/CatWMKit/Config/Script/`)

- `ConfigEngine`: the system JavaScriptCore through its public API, on its own thread with a run loop. It loads the bundled `sucrase.js` (Sucrase 3.35.1, `Tools/bundle-sucrase.sh`) once and keeps the context loaded. Only the finished value goes to the main thread.
- `ConfigRuntime`: the module registry in JavaScript. Sucrase turns `import` and `export` into `require` and `exports`, and each module runs as `function (exports, require, module)`. Every save runs the entry again from a fresh module map and keeps only the compiled functions, by file text, so Sucrase doesn't run twice on an unchanged file. A failed run, or a value that `ConfigScript` rejects, keeps the last good config and the key functions that went with it. CatWM doesn't use the native ES module loader: it's private API and keeps each old module for the life of the context.
- `ConfigCatwm`: the host module that `import { catwm } from "./catwm"` resolves to. See "The `catwm` module".
- `ConfigScript`: reads the store into `Config`. Each option's path comes from `.script(...)` in the option table. Only the paths in the value change, so reading the TypeScript value and then the overrides gives the precedence. `ConfigScript+rules` reads the recorded window and workspace rules into `Config.windowRules` and `Config.workspaceRules`.
- `ConfigWatcher`: FSEvents on the config folder and the folders of the imported files, not on the files. Editors and CatWM save by rename.
- `ConfigMigration`: turns `catwm.conf` text, or the value of an old `export default` config, into TypeScript with `Config.parse` and `BindRange`. `ConfigStore` writes the result only when it runs and gives the same `Config`, never over an existing `catwm.config.ts`, and once (`DefaultsKey.migratedConfigToTypeScript`). A failed conversion leaves `catwm.conf` in use and reports why.
- `ConfigTypes`: `catwm.d.ts` and `tsconfig.json`. The `catwm` object's types come from the option table, so a new option needs no second list. CatWM writes the types each launch, and `./build.sh` writes the same file to `Resources/AgentDocs/catwm.d.ts`.

## The `catwm` module

A config sets options as `catwm.gaps.size = 10` instead of exporting one object. We chose that over `export default` for three reasons. Every default is readable (`catwm.gaps.size + 2`), so a config can build on what it has. A small config is a few lines, not an object that repeats the structure. And a file that imports `catwm` can set options itself, so a helper module needs no return value to merge.

- **One store, merged on write.** An object assignment merges recursively, a list or scalar replaces, and `undefined` resets to the default. A list is a real array with `remove(value)` added. We rejected `clear()`: assigning `[]` does the same.
- **Writes happen while the config loads.** A write from a promise, or after the run, can't reach the result, so it is a `validate` error instead of a silent loss. `ConfigEngine.run` collects those late writes after the run.
- **No `export default` in the entry.** A default export can't be merged with the store, so in `catwm.config.ts` it is an error that shows the conversion. An imported helper may still default-export a function or a value, because in the old form only the entry's default export set the config.
- **Converted once at app launch, not accepted forever.** Accepting `export default` for good would give every config two ways to set the same options, and the docs, the types and the key functions would have to describe both. Rejecting it with only an error would leave every existing user on defaults after an update. So `AppDelegate` calls `ConfigStore.convertLegacyConfig()` before the first load, and it rewrites a file that has a default export, and the old form then has no reader to keep. It is a separate call, not part of `load()`, because tests reach `ConfigStore.shared` through `WindowManager.shared`, and a load that writes would rewrite the developer's own config. It runs the old file through `ConfigEngine(legacy: true)`: the same runtime and module registry, so imports work, but the result is the entry's `exports.default` instead of the store, and the default-export check is off. A second JavaScript runtime would have drifted from the real one. The old names move to the new ones (`ConfigMigration.renamed`, from `ConfigScript.renamed`), and the value goes through `ConfigMigration`'s writer, the one that writes `catwm.conf` as TypeScript. Writing `catwm.conf` and writing a value share the writer because the output has to look the same. The writer, which also writes the default config, puts a group with more than one option into one object (`catwm.gaps = { … }`) and keeps a lone option as a setter. One object per group reads as a config. A setter per field would read as a dump of the store, and the merge on write makes the two forms equal. The new file replaces the old only if running it gives the same `Config` as reading the old value (`ConfigStore.install`, shared with the `.conf` conversion). Otherwise the old file stays and the diagnostic says why. We rejected a text transform of the source: it would have to parse TypeScript, and running the file is the only way to get the value of helpers, spreads and imports. The price is that comments and helper constants are lost, so the original is kept as `catwm.config.ts.bak` (never over an existing backup: `.2.bak`, `.3.bak`, …). There is no flag for "done": a converted file has no default export, so the next load finds nothing to do.
- **A full re-run on every save.** The earlier design re-ran only the changed modules and the modules that import them, which needed an import graph and a cache to invalidate. With one shared store a module's writes are part of the result, so a save that changes one file would have to replay the writes of the others. Running everything again costs a few milliseconds for a config of this size (the log line `config: ran N modules in X ms` shows it) and removes that state.
- **Scoped options.** An entry in the option table can be `.scoped()`: a workspace could set it without changing anything else. The generated types, the validation of workspace rules and the `catwm.d.ts` scoped list all come from that flag.
- **Motion styles** live in one list (`MotionStyle.all`). Settings → Motion and the `catwm` module read the same list, and `catwm.motion.style = "snappy"` expands to its field values at write time, so Swift never sees `style`.

### Rules

`catwm.windows(match, win => …)` and `catwm.workspaces(match, () => …)` run their function once while the config loads, in a recording mode. A window rule records actions, such as `setfloating` and `resizeactive exact 600 500`, as the same dispatchers a key runs. A workspace rule records the scoped options its function wrote. `ConfigScript` reads both into data on `Config` (`Condition`, `WindowRule`, `WorkspaceRule`), and a RegExp becomes an `NSRegularExpression`, or a diagnostic if it can't convert. Rules are data so that the window manager can evaluate them on its own thread without running JavaScript, and so that `Config.changes` can compare them.

`WindowManager+rules` applies window rules. `refresh()` calls it for each window that appeared or changed title since the last pass, so no work happens per refresh otherwise. Each window keeps the rules that matched last time (`Window.matchedRules`), and a rule's actions run when it enters that list. A rule is known by its content, not its index, so a save that adds or edits a rule runs it on windows that are already open, and a save that only reorders rules runs nothing. We rejected re-applying on every refresh: it would snap a window back after the user moved it. The actions run through the same `WindowAction`s as a key, with `ActionContext.target` set to the window, so a rule moves its own window and never the focused one. Rules run in file order, so the later of two matching rules wins. The facts are the window's bundle ID, title, pid, workspace, display, floating, minimized and fullscreen state. There is no subrole fact, because the scanner admits only standard windows.

### Workspace rules in `refresh()`

`refresh()` resolves each visible workspace's config (`Config.resolved(for:)`, `WindowManager+workspaceRules`) right after the workspace reconciliation and before the layout asks for slots: the base config (which already holds the Settings overrides), then each matching rule in file order, last write wins per field. A rule beats a Settings override because the override only changes the base the rule starts from.

- **Resolve before layout, so no second pass.** The facts (window count, windows per app, apps, layout, name, display, focus) don't depend on the slots, so a rule that changes gaps or padding is already in effect when the slots are computed, in the same refresh. A rule can't change a fact it matches on, so nothing can loop.
- **No cache across refreshes.** A fact is a count over `visible`, the windows CatWM places on the shown Desktop (tiled or floating; minimised windows and windows of hidden apps aren't there). That costs microseconds for a few rules, and a cache would have to be invalidated by every window event. Without rules `refresh()` does one empty-list check.
- **New windows are ordered after the resolve.** `newWindowsToMain` is scoped, and a window's workspace is only known after reconciliation, so `placeArrivals` no longer inserts arrivals into `order`. `orderArrivals` does it once the config is resolved.

Everything that places a window reads the resolved config of that window's workspace (`config(on:)`, `motion(of:)`). Readers that aren't tied to a workspace (panels, the tab strip's own fades) keep the base config.

### Floating: the latest change wins

Floating has three sources: `floating.apps` (through `Window.autoFloating`), a rule's `setfloating` or `settiled`, and the user's toggle. We rejected a fixed ranking. A user who tiles one Calculator window wants it to stay tiled, and a user who lists an app after tiling its windows wants them to float. Each source writes `Window.userFloating` when it fires, and `isFloating` reads that, so the last write wins and no source needs to know about the others. A save fires only for windows whose result changed. `applyFloatingChanges` compares the result before and after the save (the last matching rule's float or tile, else the list) and writes `userFloating` for a window that differs, or clears it to `.automatic` when no rule decides it. A save that changes nothing for a window leaves its toggle alone, so a save never undoes the user's toggle by itself.

### Key functions

`catwm.bind(mods, key, () => …)` keeps the function in a table on the config thread and writes a reference (`{function: N}`) into the bind. The table is replaced only after a run succeeds. Pressing the key calls `ConfigEngine.call(function:window:event:state:)` with a snapshot of the focused window. The call runs off the main thread and main never waits on it: `ConfigStore.call` hands the request to the engine thread and returns, and the result comes back on main as the recorded actions. `WindowManager.run(_ binding:)` runs each on the window that was focused at the press, not the one focused when the result arrives, because the user can change focus during the hop. The hotkey handler of both surfaces calls it, so the app and embedded mode share one path. Actions still run if a save replaced the config in between, because the actions are plain data and a guard would drop a key the user did press. A throw or a timeout runs no actions and reports like a config error.

### Event handlers

`catwm.on(event, fn)` is the same mechanism as a key function, so a handler has the same limits: it keeps `fn` in the table and writes `{event, function}` into the `eventHandlers` list that `ConfigScript` reads into `Config.eventHandlers`. The event name is checked against `EventBus.allNames`, and `catwm.d.ts` gets its `Events` type from `EventBus.specs`, so a new event is one `EventSpec` and nothing else.

- **A bus listener only while a handler exists.** `WindowManager.syncEventHandlers` registers one `EventBus` listener when `Config.eventHandlers` becomes non-empty and drops it when it empties. `EventBus` diffs state only while it has a subscriber, so a config without handlers costs what it did before. We rejected a standing listener that checks the list: it would keep the diff running for every user. The listener is one for all events, and filters by name when an event arrives, so the work for an event nobody handles is a list scan.
- **The window is the event's.** The result comes back on main like a key function's, and its actions run with `ActionContext.target` set to the window in the event data. If that window is gone by then, the actions are dropped, except for `window.removed`, where no window can be the target and the actions run as a key would. We rejected falling back to the focused window for the other events: the user could have changed focus during the hop, and a handler would then float or close the wrong window.
- **After the event, not before.** The events come from diffing a snapshot after `refresh()`, so a handler can't take part in placing a window. That belongs to `catwm.windows` rules, which `refresh()` runs while it places. We rejected making a handler block the refresh: main never waits on the config thread.
- **`catwm.dispatch` and `catwm.state`.** `dispatch(name, ...args)` pushes one recorded action, like the handle's methods but for any dispatcher, so a handler and a key function use the same call. `catwm.state` is a snapshot that `WindowManager.scriptState` builds from `StateSnapshot` at call time and sends as JSON text. JavaScript parses it on first read, so a function that never reads it pays only for the text. It has no live view: a function can't ask main anything, and a stale answer would be worse than a snapshot that is dated by its call. Windows carry only the fields an event also carries (app, title, floating, workspace), to keep it small.
- **A workspace is a name that a window, a display or a state entry holds.** `StateSnapshot.workspaceNames` is the union of the workspaces of windows, the workspaces that displays show and the keys of `states`. `workspace.created` and `workspace.removed` come from that set changing. We rejected a separate registry of workspaces: the manager has none, and one more list would have to agree with the rest.
- **`window.changed` is title, floating and workspace.** The first workspace a window gets isn't a change, because every new window gets one a refresh after it appears.

## Start-up cost

The first load pays for the whole engine: a JavaScript context, Sucrase and a cold first transform. The first-load perf row measures it, and the hot-reload row measures the saves after it. We chose to shrink that work and rejected skipping it.

- `Tools/bundle-sucrase.sh` patches three start-up costs out of Sucrase and fails the build if a patch stops matching: a 65,536-step table loop, a 9,000-element array literal that JavaScriptCore compiles one element at a time, and the option checker, which CatWM's constant options never need. `Tools/embed-sucrase.py` writes the bundle as ASCII, because JavaScriptCore lexes 8-bit scripts faster and keeps them at half the size.
- A transform cache on disk, or loading Sucrase only on a miss, would skip the cost on a repeat launch. The first save after a launch would then pay for Sucrase, and that save is the one the hot-reload row measures. A bytecode cache needs `JSScript`, which this macOS doesn't have.
- The first run collects garbage at once, with the exported `JSSynchronousGarbageCollectForDebugging` and `JSGarbageCollect` as the fallback. JavaScriptCore otherwise collects the start-up garbage during the first save, and that save takes twice as long as the rest. The cost moves into the first load, which has the room.

## Applying a change

`WindowManager.apply` compares the new `Config` with the old one (`Config.changes`) and applies only what differs. A bind change calls `surface.apply` and lays out nothing. A Desktop slide stops only when `virtual-workspaces` or `workspaces-per-display` changes. `refresh()` runs only for a field outside `WindowManager.liveFields`. An unchanged config with the same diagnostics does nothing, so the watcher event after an overrides write is free.

## Errors

A failure is a `ConfigDiagnostic`: file, line, phase (`read`, `resolve`, `transform`, `evaluate`, `validate`, `migrate`) and message. `ConfigStore.failures` holds the last failure until a good save. A script that runs longer than `ConfigEngine.timeLimit` (1 s of CPU time), such as an endless loop, counts as a failure. The private `JSContextGroupSetExecutionTimeLimit` stops it, usually within about 2.5 s of wall time. The engine then rolls its module registry back and keeps the last good config, and the next save runs on the same thread. A run that still hasn't returned after `ConfigStore.timeLimit` (5 s), for example in a native call, makes CatWM stop waiting and start a new engine. That old thread keeps running until CatWM quits. The menu bar menu shows it, and `config.reloaded` sends every diagnostic in `errors`.

## Settings

Settings and `config.set` never write the TypeScript file. `ConfigDocument` edits `ConfigStore.settingsText` and reloads it after each save of the TypeScript config. A Settings save takes only what changed from the text it loaded, puts it on the running config, and writes the values that differ from the TypeScript config (`ConfigStore.base`) as overrides. So a value that the `.conf` text can't hold, such as a command with a line break, keeps its TypeScript value. Settings → General lists the overrides and drops one with **Use File Value**. Saved presets in `configs.json` keep their `.conf` text and apply through the same path.

## Embedded mode

`ConfigStore(embedded: true)` starts from `Config.embedded`, with every feature off, and reads the entry file that the host gives (`use(entry:)`). It writes no files: no migration, no default config, no `catwm.d.ts`, and it keeps the overrides in memory. `ConfigScript.read(embedded: true)` rejects the features that embedded mode doesn't have. See `docs/internals/embedding.md`.
