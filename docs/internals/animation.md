# Animation

All animation code lives in `Sources/CatWMKit/Motion/` (window, Desktop and curve engine) and `Sources/CatWM/Motion/` (SwiftUI and layer helpers), and nothing else may start an animation. `Tools/check-style.sh` enforces this, and a `// style-ok` escape on such a line is itself an error. `App/Perf/FrameRun.swift` may use a display link because it measures frames, and the mode cursor and the Sort drag may run fast timers. The user's animation settings reach every kind of motion through one value, `MotionSpec`, so a setting change moves windows, Desktops and panels alike.

## Window frames

CatWM animates real windows by writing AX frames, so the app's resize and redraw latency still shows in the motion. A display link can pace the writes, but it can't remove that cost. A compositor such as [Hyprland](https://github.com/hyprwm/Hyprland/blob/main/src/render/pass/SurfacePassElement.cpp) fits the client's current buffer to the animated geometry instead. macOS gives a window manager no such hook.

`Animator` steps on an `NSScreen` display link for the fastest display that holds an active destination. Pending writes coalesce, so a slow app skips obsolete frames instead of replaying them.

## Lead prediction

What the user sees trails what CatWM writes by the AX call plus the app's redraw, so each writer samples the trajectory at the time its write will be on screen. `WindowLead` holds that model per window as pure maths, and `AXWriter` owns one per window on its queue.

**Sample at the vsync the write lands on.** A write from a callback can show at that callback's `targetTimestamp` at the earliest. The writer samples each axis at `targetTimestamp + k × period`, where k rounds (call completion + redraw delay + bias − `targetTimestamp`) to whole frames. The window server shows frames only at vsyncs, so a lead between two vsyncs would only add error. The period is the link's `targetTimestamp − timestamp`, never a constant, so a 120 Hz display leads more frames for the same delay. It rounds to the nearest frame rather than up, because a learned delay already holds the vsync slack of the observation it came from. The cost: a delay learned at one call phase can be a frame off when the phase moves, for example when the call order flips between moves in opposite directions, until the median relearns. One phase can't separate the redraw time from the slack.

**Learn the delay by matching written values.** Each tick, main reads one SkyLight frame per moving window (`Animator.readFrame`) and attaches it to that window's step. The writer keeps its last writes with the time each AX call returned. When a visible origin or size changes to a value it wrote, the delay is the observation's vsync minus that call's return. Inverting the trajectory, as the meter does for lag, was rejected. It returns the sample time of the visible write, which the lead itself chose, so the estimate would chase its own output, and it costs about 100 trajectory evaluations per window per tick on main. Matching also rejects what it can't attribute. An axis that didn't change, a size the window refused, a write the app ignored and a change seen across a dropped callback teach nothing, because the change could belong to either vsync.

**Position and size apart.** Each axis has its own delay and its own call cost and is sampled at its own time, because apps move a window long before they redraw it at a new size, and one shared lead leaves the origin ahead or the size behind. An axis with no samples borrows the other's delay. Completion follows the order the writer will issue the calls (`WindowFrameOrder`), since the second call returns after both calls' cost. The order depends on the frame, so the writer plans, finds the frame's order, and replans when it differs. The cost: under jitter, two independent estimates can split by a frame and lead one axis ahead of the other. Sharing one estimate when the axes are within half a frame was tried and changed nothing measurable.

**No new lock on main.** The observation rides in the step request, which already takes the writer's lock once per window per tick. The writer never holds that lock during an AX call, so main can't wait behind a slow app. Observations queue per window, bounded, so a coalesced step doesn't lose the tick a change first showed. All learning runs on the writer's queue. Main reads the estimate once per new move, to start its trajectory. The read is the only SkyLight call per tick, and the meter and the color fill reuse it.

**Stable over exact.** A lead that changes between ticks injects velocity error, which looks worse than a steady lag. The delay is the median of the last `leadSamples` samples, each capped at `leadLimit`, so one stall or dropped frame can't move it and a real change takes three samples. The frame count holds until the estimate passes the rounding boundary by `leadHysteresis` of a frame, so a delay near a boundary doesn't flip between two vsyncs. The lead (cost and delay) is capped at `leadLimit`. The writer's own lateness isn't, so a writer far behind writes the current frame instead of an old one. A lead can't carry a frame past the target, because a trajectory clamps at its end. A bounce curve's overshoot belongs to the curve.

**Start where the first write shows.** A new move starts its trajectory at its first tick, at `timestamp + k × period` with k the frames its first write needs, so the first visible write is the curve's first step. Starting at `animate` skipped the start of the curve, which ease-out makes its fastest part, and made a slow app's first frames trail by its whole latency. A move that retargets a running one still starts at `animate`, from the old trajectory's value and velocity, because the window is already moving and its writes in flight continue the old curve. The price is that a move starts up to k frames after the command, when the window couldn't have moved sooner anyway.

**Remember between moves.** A move lasts about seven frames, and a delay needs two frames before its first sample, so without memory every first move would trail. Each window keeps its delays for `leadMemory` after its last sample, and a window with none starts from its app's most recent learner. That's ten seconds, against the write cost's one second, because redraw latency comes from the app's content and changes over seconds to minutes, while the write cost tracks a momentary stall. A stale delay is a frame or two off and relearns in three samples. The write cost keeps its old rules: samples only from successful writes, capped at `writeCostLimit`, rising at 80% weight and falling at 40%.

## Landing

A window that `Animator` writes stays busy for `MotionTiming.quietAfterWrite` after its last write, so the AX echo of CatWM's own move doesn't read as a user move. An app that ignores a write sends no event, so `LandingCheck` reads each landed window back after `MotionTiming.landingCheckDelay` and writes the target once more. A window that stays larger teaches the layout its minimum size, and one whose top edge stays lower teaches it the menu bar. One epoch per window says whether a landing callback or a check is still current, and a cancel bumps it.

Focus writes don't belong to motion, so `FocusWriter` in `Tiling/Focus` owns them. They run on a queue per app apart from the frame writer's, so focus never waits behind a slow app's frame writes.

## One motion per screen

A refresh animates each screen's moves with the motion of that screen's workspace (a workspace rule can change it), so `applyTileMoves` hands the animator one batch per screen, and `maxAnimatedMoves` counts per batch. Moves that must not animate go first in a batch of their own and land at once.

## Color fill

A color fill keeps the real window live and paints sampled edge colors over the part of the animated outline the window hasn't reached, so the outline moves on the trajectory whatever the app does. `lab.resizeAnimation` picks `color-fill` (the default) or `live`. A third mode, `snapshot`, scaled captured windows in a panel. It was removed because capture added tens of milliseconds before every resize and had to fall back to live motion whenever another window overlapped. A config that still names it gets the default, so an old setting can't block a config load.

**On only if Screen Recording is already allowed.** The colors come from a window capture. `AppSurface` installs the fills when the setting is `color-fill` and `PermissionWatcher` already reports Screen Recording, and follows the watcher when that changes. The watcher reads off main with `CGPreflightScreenCaptureAccess`, which never prompts, and Settings shows no reminder, so the feature never asks for the permission. Without it nothing is installed: no warm-up, no capture and no work per tick, and windows move live with the lead. A third value, `auto`, was rejected because `color-fill` already falls back when it can't capture, so the two would behave the same. The option stays in `lab`. Moving it would be a rename, and `ConfigScript.renamed` makes an old key a load error, which would break every config that sets it to turn fills off.

**One rule for when it engages.** `WindowFillPlan` decides and shapes every fill, and the bench uses it too, so the bench measures the real rule. A move engages when its window has a cached appearance, its size changes, both frames are at least the appearance's corner size, and both are on one display whose scale matches the capture. A move that only translates stays live, because the inside rule below would turn it into resizes, and every resize costs the app a redraw. The decision is per window: an uncached, translucent (no appearance) or cross-display window moves live, and the rest of the batch keeps its fills.

**Why the top edge used to be fixed.** The side colors are one-pixel columns of the capture, indexed from the window's top, so the titlebar and toolbar rows line up with the live window only where both tops meet. The fill hung them from the outline's top, so any vertical offset drew a titlebar band at the wrong height, and the engagement rule, the per-tick check and `retarget` all required the same top. The fix: the columns hang from the live window's top, and the band between the outline's top and a lower window top takes the titlebar color (`topColor`, the column's row at the corner radius). The capture's height no longer has to match: rows past it take the bottom color, as height growth always did.

**Keep the window inside its outline.** A fill hides a window that arrives late or is too small, but nothing hides one that sticks out. So under a fill each edge takes the inner of the trajectory at its predicted vsync and `fillAhead` (8 ms) later: an edge moving inward leads, and an edge moving outward samples on time. The origin is shaped at the position's vsync and the size at the size's, because the two show at different vsyncs: a frame mixed from one write's origin and another write's size spilled 180 px in a swap. The lead bias that part 3 left (one scalar per window, added to the lead) was rejected and removed. A swap or a stack open moves some edges of a window inward and others outward, so one time shift pushes half of them out. Larger margins were measured: 17 and 33 ms cut ratio spill further but turned most of a swap into flat color, and a margin that held outward edges back raised spill. What's left is the first frames of an app with nothing learned, before any write has shown, which no geometry fixes.

**Cut for the next vsync.** The fill commits for the next vsync, but the newest native frame is from this one. Cutting the hole at that frame left a frame-wide strip of desktop on each inward edge. The hole is the rect inside the window whichever of its observed and expected (one frame further) origin and size shows, since origin and size show apart. When the window moves further than its own size in a frame, that rect is empty, and the hole falls back to the overlap of the observed and expected frames.

**Reads.** A tick reuses the frame `Animator.tick` already read for the lead. Only a window whose fill outlives its trajectory (landing, or following a divider) reads its own. Window order, levels and the frames of windows in front are read once per move, when it starts, against each window's source-to-target bounds: a window in front drops only the fills it covers. The panel is ordered above its window when it appears, not every tick. A window raised mid-move covers the fill as it would cover the window, and a moving window raised over its own fill still shows it, because the fill paints only outside the window. Re-reading the order each tick cost a list call plus a level, often a frame, per window in front, and bought nothing visible.

**Warm-up off the motion path.** Appearances are captured and decoded on a background queue while no move runs. A pass reads the window order once and one frame per window on main. A window without an appearance when its move starts moves live for the whole move. A capture that lands mid-move waits for the next one, so a fill never appears partway. That's the first move after launch and the first move of a new window.

The fill samples narrow side bands, a bottom row and the border and alpha outline, and takes the most common color per band to reduce streaks from text. Bottom growth stretches the longest flat color run, which is a guess at which region grows, such as a sidebar. There's no app whitelist. It supports opaque rectangular and rounded windows on one display. True transparency would need a different method. Within a tick, writes that release space go first, and position and size go in whichever order keeps the intermediate rectangle closest to the source and target union. Without that, a right-aligned tile briefly extends off its display. `Tools/window-fill-probe.sh` checks the pixels (seams, borders, corners, everything outside the target), not the latency.

## Motion quality

A successful AX write doesn't show when the app draws, so `MotionRun` measures the window-server frame instead, from the read the lead takes each tick. At each display-link callback it compares that frame with the trajectory at the callback's `timestamp`, the vsync on screen now. The `targetTimestamp` would be wrong here. The writes from this callback can't show yet, so it would charge every app a frame, even one that draws at once.

`MotionQuality` keeps these numbers per window and tick. Error, spill and gap are the largest edge distance in points, not an area, because the eye catches the one edge that's off. Spill is how far the native window reaches outside the desired frame, and gap is how far it falls short. They stay apart because a fill can hide a gap but nothing hides a spill. While a fill shows, gap is what its hole leaves bare (how far the window falls short of the hole inside the outline), and cover is how far the window falls short of the outline, the part shown as edge color instead of content. Lag inverts the trajectory along its fastest edge. Dividing the error by the speed would be simpler, but the curve isn't linear, and the fastest edge gives the finest time step. An edge slower than 100 px/s gives no lag sample, because a point there spans 10 ms or more.

Error alone can't tell a steady lag from a jittery one, and a predictor that guesses wrong in alternate frames can have a good mean. Stutter is the per-frame velocity error: how far one frame's edge step differs from the trajectory's step over the same frame, in points per frame, because a hitch is a jump between two frames. Overshoot counts only edges that travel and only past their target, so a spill along an edge that shouldn't move stays a spill. The tail is the time from the trajectory's end until the window rests on its target. In measuring mode the display link runs on after the last item lands until each window rests or `MotionQuality.tailLimit` passes, since the tail happens after the motion it belongs to. The meter runs only in verbose mode or when a caller sets `measures`. Each tick it reads one more frame per settling window and searches about 100 trajectory times per moving one, outside the tick cost it reports.

`MotionBench` (`Tests/Fakes`) runs the real `Animator` and `AXWriter` on a virtual clock. Each writer queue is held between frames, so coalescing is real and every run gives the same numbers. The fake applies an AX write at once, and the window-server frame shows it after the app's latency. Position and size have their own latency, because some apps move a window long before they redraw it at a new size. Profiles a predictor can't fit by one constant sit next to the steady ones: latency that changes mid-run, a dropped display-link callback, a 120 Hz display and an app that ignores every third write. A warm run moves the windows back first, so it shows what memory between moves buys. The predictor learns from this fake, so a result that depends on the fake's latency model (a fixed delay, independent noise per axis, an exact phase) says less than one that follows from the algorithm (the start, rounding to vsyncs, rejecting what can't be attributed). Panels and captures need a screen, so the bench's color fill keeps only bookkeeping and calls `WindowFillPlan` with a flat appearance. Nothing covers its windows unless a run marks one obscured. Its tick cost leaves out the SkyLight reads.

## Trajectory inherits velocity

Restarting a curve from rest when a target changes mid-flight makes the item stop and start again. `Trajectory(…, velocity:)` uses inertialization instead. It adds `carry * u * (1 - u)^2`, where `carry = velocity * duration - (to - from) * slope0` and `u` is normalized time. The term is 0 at both ends, so the motion still starts at `from` and lands on `to`. Its slope is `carry` at the start and 0 at the end, so the speed starts at the carried velocity and the curve's own landing is untouched.

`DesktopMotion` uses this for reversals. It remembers its last value, time and speed, builds the new trajectory from there and shortens the spec in proportion to the remaining distance. A swipe feeds `follow(until:update:)`, so the slide that follows starts at the finger's speed.
